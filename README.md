# Monoclo Quick Order

Швидке замовлення («Замовити в 1 клік») для Shopify-магазину Monoclo замість ручного коду в темі.
Замовлення приходить менеджерам у Telegram з кнопками «Взято в роботу» / «Спам».

```
Сторінка товару ──► App block (кнопка) + App embed (попап)      extensions/quick-order
        │ POST /apps/quick-order/submit
        ▼
Shopify App Proxy (підписує запит) ──► server/  (Node 22, без залежностей)
                                         ├─ перевіряє підпис і магазин
                                         ├─ валідує дані, ліміти, захист від дублів і спаму
                                         ├─ бере ціну й наявність із /products/<handle>.js
                                         └─ шле повідомлення в Telegram
```

## Що змінилося порівняно з кодом у темі
- Токен Telegram більше не потрапляє в браузер: він лише в змінних оточення сервера.
- Ціна й наявність перевіряються на сервері, форма не може підмінити суму.
- Один раз вмикається app embed, і кнопка додається блоком на будь-якому шаблоні (худі, футболки…).
- Новий попап: панель справа на десктопі, bottom sheet на мобільному; кнопка неактивна, доки не обрано
  колір/розмір, імʼя й телефон; недоступні розміри перекреслені; залишок; маска телефону +380;
  екран успіху замість зникаючого тосту; запамʼятовує імʼя й телефон.

## Запуск локально

```bash
npm install
npm test                 # тести бекенду
npm run preview          # збирає preview/out/index.html з реальних Liquid-блоків
npm run preview:shots    # E2E у Chromium + скріншоти (preview/out/shots)
```

Прев'ю відкривайте як файл у браузері. Параметри: `?mode=network|soldout|invalid` (помилки відправки),
`?hours=off` (імітація неробочого часу).

## Налаштування

### 1. Telegram
1. У @BotFather створіть бота (`/newbot`) і візьміть токен.
2. Заповніть змінні `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_WEBHOOK_SECRET` (див. `.env.example`).
3. Додайте бота адміністратором у групу замовлень.
4. Після деплою відкрийте в браузері (підставивши свої значення):
   `https://api.telegram.org/bot<ТОКЕН>/setWebhook?url=<СЕРВЕР>/telegram/webhook&secret_token=<СЕКРЕТ>&allowed_updates=["callback_query","message"]`

### 2. Shopify
1. Створіть додаток у Shopify Dev Dashboard, тип розповсюдження: custom (один магазин).
2. `client_id` і адреси сервера вже в `shopify.app.toml`. Client secret → змінна `SHOPIFY_API_SECRET` на сервері.
3. `npx @shopify/cli@latest app deploy`, потім встановіть додаток на магазин `SHOPIFY_SHOP`.
4. Customize → **App embeds** → увімкніть **Quick Order popup**; на шаблонах товару додайте блок **Quick Order button**.

### 3. Хостинг (Render)
- Web Service, Docker, гілка з кодом, health check `/healthz`.
- **Disk:** Mount Path `/data`, 1 GB. Без нього база (замовлення, черга, ліміти) губиться при кожному перезапуску.
- Один інстанс (SQLite).

### 4. KeyCRM (необовʼязково)
Змінні `KEYCRM_API_KEY`, `KEYCRM_SOURCE_ID`, за потреби `KEYCRM_STATUS_MAP`. Помилки KeyCRM не зупиняють
Telegram: замовлення повторно відправляється з чергою, а після 10 невдалих спроб у групу приходить попередження.

### 5. Моніторинг
- `GET /healthz` для Render (завжди 200, поки процес живий).
- `GET /status` для зовнішнього моніторингу (UptimeRobot): `503`, якщо база недоступна або замовлення
  понад 10 хв не може відправитись у Telegram.

### 6. Оплата через Monobank (необовʼязково)
Змінні `MONOBANK_TOKEN`, `PREPAY_AMOUNT_UAH` (за замовчуванням 200), `PAY_MAX_AMOUNT_UAH` (50000), за потреби
`KEYCRM_PAYMENT_METHOD_ID`. Під замовленням у Telegram зʼявляються кнопки:

- **💳 Передоплата 200 ₴**: рахунок на суму передоплати;
- **💳 Повна сума / Залишок**: рахунок на всю суму (або на залишок після вже отриманої оплати);
- **✏️ Інша сума**: бот просить менеджера відповісти на його повідомлення числом (наприклад, сума після промокоду),
  і створює рахунок на цю суму.

Бот пише менеджеру готовий текст для клієнта (один дотик, щоб скопіювати) і вказує, хто створив рахунок. Якщо
створити рахунок на іншу суму, старий неоплачений закривається. Коли клієнт платить, банк надсилає вебхук
`/mono/webhook`, підписаний ECDSA (перевіряється відкритим ключем банку); бот пише в групу, скільки сплачено й який
залишок, а оплата фіксується в KeyCRM. Вебхук без дійсного підпису відхиляється.

Щоб працювала кнопка «Інша сума», вебхук Telegram має приймати і відповіді (`message`), тому після оновлення
виконайте `setWebhook` з `allowed_updates=["callback_query","message"]` (див. розділ про Telegram).

### 7. Нова пошта: місто, відділення, поштомат, адреса (необовʼязково)
У формі зʼявляється випадаючий список міст з API Нової пошти. Після вибору міста клієнт обирає спосіб доставки:
**Відділення**, **Поштомат** або **Адресна** (вулиця зі списку, будинок, квартира). Дані йдуть у повідомлення
Telegram і в KeyCRM (служба доставки, місто, область, відділення/адреса отримувача).

- Змінна `NOVA_POSHTA_API_KEY`: ключ з кабінету my.novaposhta.ua (Налаштування → Безпека → Ключі API). Ключ лежить
  лише на сервері; сайт звертається до `/apps/quick-order/np/*`, а ці запити підписує Shopify.
- `KEYCRM_NOVA_POSHTA_SERVICE_ID`: службу доставки «Нова пошта» в KeyCRM (щоб замовлення мало правильну службу).
- Налаштування app embed: «Списки Нової пошти» (вимкнути, щоб місто вводилось вручну) і «Робити доставку обовʼязковою»
  (за замовчуванням вимкнено, щоб не знижувати кількість замовлень).
- Якщо Нова пошта недоступна або ключа немає, форма працює зі звичайним текстовим полем міста, а замовлення не блокується.
- Якщо KeyCRM не приймає поля доставки (422), замовлення створюється без них, а доставка лишається в коментарі менеджера.

## Заявка «Свій принт» (форма-бриф на лендингу)
Форма на сторінці `/pages/svii-prynt` (секція теми `sections/mcl-custom-brief.liquid`) шле `POST /apps/quick-order/custom`
(сервер: `/proxy/custom`). Перевірки ті самі, що й у швидкого замовлення: підпис App Proxy, ліміти за IP і номером,
honeypot, захист від дублів. Далі все як у швидкого замовлення: картка в ту саму Telegram-групу
(«🎨 Свій принт · заявка #…», кнопки чатів, оплати й статусів), замовлення в KeyCRM, передача покупки в рекламу після ТТН і оплати.

- Поля: `item` (`tee`, `hoodie`, `kids`, `a3`, `a2`), `quantity` (1…`MAX_QTY`; `MAX_QTY` = «10+», гурт), `color`, `size`,
  `placement` (`back`, `front`, `both`), `idea` (до 280 символів, у коментар), `name`, `phone`, `utm`, `ads`, `client_id`, `website` (honeypot).
- Ціна - з таблиці `server/custom-print.js` (форма не може її змінити). Змінити без деплою: `CUSTOM_PRINT_PRICES={"tee":1450,"hoodie":2450}`.
- Фото: після заявки браузер стискає кожне фото (до ~2000 px, JPG) і надсилає окремо на `POST /apps/quick-order/custom/photo`
  (`order_number`, `client_id`, `image` base64, `index`, `total`). Сервер приймає лише JPG/PNG/WEBP (перевірка за вмістом),
  до 3 МБ, до 5 фото на заявку, лише з того самого браузера і протягом години; фото не зберігаються - одразу йдуть у
  Telegram відповіддю на картку заявки (якщо не приймається як фото - документом).
- Товару в магазині немає: `variantId` - варіант чернетки «Власний принт MONOCLO» (`vlasnyi-print-zamovlennia`), щоб покупка мала стабільний ідентифікатор.

## Подарункові сертифікати «Свій принт»

Сертифікат продається на сайті звичайним товаром «Подарунковий сертифікат «Свій принт»» (варіанти Виріб × Формат:
електронний за ціною виробу або друкований +150 ₴). Подарункова карта Shopify не підходить: замовлення йдуть через
GetCheckout, де її код не видається й не вводиться.

- **Видача коду.** Раз на `CERT_POLL_MINUTES` (10 хв) сервер переглядає замовлення KeyCRM за останні `CERT_LOOKBACK_DAYS` (3) дні
  (усі джерела або лише `CERT_SOURCE_IDS`), знаходить рядки з назвою, що містить `CERT_PRODUCT_MATCH` («сертифікат»),
  і на кожну штуку створює код `SP-XXXXXX`. У групу приходить картка: код, виріб і сума, формат (електронний - надіслати
  після повної оплати; друкований - вкласти листівку в посилку), оплачено з KeyCRM і готовий текст для покупця з посиланням
  `/pages/svii-prynt?cert=SP-XXXXXX#brif`. Повторний перегляд того самого замовлення нових кодів не створює.
- **Сума.** Виріб береться з варіанта (Футболка, Худі, Футболка дитяча, Постер A3/A2) за таблицею цін «Свій принт»;
  якщо виріб не розпізнано - ціна рядка мінус 150 ₴ за друк.
- **Погашення.** Кнопка «✅ Погасити сертифікат» (і «↩️ Скасувати погашення») на картці сертифіката. Якщо клієнт вказав код
  у брифі, у картці заявки є рядок про сертифікат (дійсний / вже погашено / не знайдено), а під нею - кнопка погашення.
  Менеджер може просто написати код у групі - бот відповість станом і кнопкою.
- Коди видаються лише для замовлень, створених після першого запуску функції (або після `CERT_FROM`). `CERT_ENABLED=0` вимикає.

## Що вміє сервер
- **Надійність:** замовлення спершу зберігається в SQLite, потім відправляється. Якщо Telegram/KeyCRM недоступні,
  черга повторює з наростаючою паузою (30 с … 15 хв); менеджер бачить позначку «надійшло із затримкою».
- **Статуси:** ✅ В роботі · 📵 Не відповів · 👍 Підтверджено · 📦 Відправлено · 🚫 Скасовано · ❌ Спам. Статус зберігається
  в базі, дописується в повідомлення і (якщо налаштовано `KEYCRM_STATUS_MAP`) оновлює замовлення в KeyCRM.
- **Нагадування** (можна обмежити змінною `REMINDERS_FROM`, щоб старі й тестові замовлення не нагадували): якщо замовлення не взяли в роботу за 15 хв (нічні рахуються від 10:00), бот нагадує в групі
  кожні 30 хв, до 3 разів, лише в робочий час.
- **Тижневий звіт:** понеділок 09:00 (Київ): кількість, сума, статуси, середній час відповіді, топ товарів, джерела.
- **UTM:** мітки реклами запамʼятовуються на 30 днів і потрапляють у Telegram та KeyCRM.

## Події для аналітики
Після успішного замовлення: подія `quickorder:submitted` на `document`; `dataLayer.push({event: 'quick_order', quick_order: {...}})`
для Google Tag Manager; `gtag('event', 'generate_lead', …)` для GA4 і `fbq('track', 'Lead', …)` для Meta Pixel
(вмикаються в налаштуваннях app embed).

## Тема попапа
За замовчуванням світла з 06:00 до 17:00 за київським часом і темна ввечері та вночі. Режим і години
змінюються в налаштуваннях app embed (також «як у пристрої», «завжди світла», «завжди темна»).

## Другий магазин: Morning Star
Сервер приймає замовлення і з Morning Star: вони приходять у той самий бот і групу з позначкою **Morning Star** у
заголовку і тегом `#MorningStar`, у KeyCRM — у джерело «MorningStar QuickOrders» (215). Кнопки статусів і нагадування
працюють як для Monoclo. Оплати Monobank, ТТН з бота і передача покупок у Meta/GA4/Google Ads — лише для Monoclo.

1. Dev Dashboard → новий додаток **Morning Star Quick Order** (custom, магазин morning-star-1883). Скопіюйте client_id
   у `shopify.app.morning-star.toml`.
2. `npx @shopify/cli@latest app deploy --config morning-star`, потім встановіть додаток на магазин Morning Star.
3. На Render додайте змінні `MS_SHOP=morning-star-1883.myshopify.com`, `MS_API_SECRET` (client secret нового додатка),
   `MS_STORE_ORIGIN=https://morningstar.com.ua`, `MS_KEYCRM_SOURCE_ID=215`.
4. Форма на сайті Morning Star (тема Dawn, секція «MS · Швидке замовлення») шле на `/apps/quick-order/submit`.

## Відомі обмеження
- Ukrainian-маска телефону (+380); міжнародні номери попап не приймає.
- Кнопка «Подзвонити» в Telegram неможлива (Telegram не дозволяє `tel:` у кнопках), але номер у тексті клікабельний.
- Швидке замовлення не створює Draft Order у Shopify (за потреби додається окремим кроком).
- Бази SQLite достатньо для одного сервера; при значному зростанні навантаження варто перейти на PostgreSQL.

## 8. ТТН Нової пошти

Після успішної оплати (передплата чи повна сума) під повідомленням «✅ … отримана» зʼявляється кнопка **📦 Створити ТТН**.
Сервер створює одержувача й накладну в кабінеті Нової пошти: відправлення з відділення №31 (Чернівці), пакет 1 кг 30×25×5 см,
оголошена вартість = сума замовлення, доставку оплачує одержувач, післяплата (послуга «Контроль оплати») = сума замовлення мінус сплачене.
Номер ТТН надсилається в Telegram і записується в KeyCRM (трекінг-код). Повторний клік дубль не створює.
Потрібне прізвище одержувача: окреме поле у формі або «Імʼя Прізвище» в полі імені.
Налаштування: змінні `NP_SENDER_*`, `NP_WEIGHT_KG`, `NP_*_CM`, `NP_DESCRIPTION` (див. `.env.example`).

## 9. Надійність і захист від дублів

- **Замовлення**: однакові заявки (подвійний клік, повтор після обриву) зберігаються один раз, у тому числі коли надходять одночасно.
- **KeyCRM**: перед створенням замовлення сервер шукає його за `source_uuid` (`quick-<номер>`), тому повторна спроба після збою не створює дубль.
  Платіж Monobank додається в KeyCRM один раз (перед додаванням перевіряється номер рахунку в описі платежів замовлення).
  Статус замовлення й номер ТТН дописуються фоновою чергою, якщо перший запит не пройшов. Замовлення в стані `failed` повертається в чергу раз на 6 годин.
- **Monobank**: якщо вебхук не дійшов, фонова звірка (`GET /api/merchant/invoice/status`, перші 3 хв, далі кожні 5 хв першу годину і кожні 30 хв) підхоплює оплату; публічний ключ не запитується частіше за раз на 10 хв; підпис вебхука перевіряється завжди; старіші за вже оброблене повідомлення (`modifiedDate`) ігноруються; повернення коштів остаточне й показується менеджеру окремо.
  Створення рахунків для одного замовлення не виконується одночасно.
- **Telegram**: повторний апдейт з тим самим `update_id` ігнорується; помилка обробки не повертає 5xx (щоб Telegram не повторював дії).
- **ТТН**: повторне натискання кнопки дубль не створює; ТТН, що вже існує, не видається за невдалу, навіть якщо збій стався при відправленні повідомлення.

## 10. Покупка для реклами (Meta, GA4, Google Ads)

Заявка у формі — це лід (`Lead` / `generate_lead` у браузері). **Покупкою** швидке замовлення стає, коли в ньому є
**і оплата, і ТТН**. Їх додає бот (Monobank, кнопка «Створити ТТН») або менеджер вручну в KeyCRM: сервер перевіряє
замовлення в KeyCRM (до 2 діб раз на 20 хв, до 7 діб раз на 2 год, далі раз на 6 год, до 30 днів).
Кнопки статусу в Telegram («Спам», «Скасовано») на покупку не впливають: менеджери інколи тиснуть їх помилково
або пропускають, тож вирішує лише KeyCRM. Щоб тестове замовлення не пішло в рекламу, не додавайте йому оплату й ТТН
або скасуйте його в KeyCRM. Не зараховуються статуси KeyCRM зі списку `CONVERSIONS_EXCLUDE_STATUS_IDS`
і групи `CONVERSIONS_EXCLUDE_STATUS_GROUPS` (за замовчуванням 6 = «Скасовано»). Якщо KeyCRM недоступний,
покупка не зараховується, доки статус не вдасться перевірити.

Покупка відправляється один раз у кожен канал, у **гривнях**, з сумою з KeyCRM (враховує промокоди):
- **Meta Conversions API:** `Purchase`, `event_id` = `quick-<номер>`, хеші телефону, імені, прізвища й міста,
  cookie `_fbc`/`_fbp` і user-agent з форми. Подія має бути не старшою за 7 днів.
- **GA4 Measurement Protocol:** `purchase` з `transaction_id` = `quick-<номер>`, client_id і session_id із cookie,
  щоб покупка прив'язалась до рекламної сесії. Не старша за 72 години.
- **Google Ads:** `GET /conversions/google-ads.csv` (логін і пароль) — офлайн-конверсії за gclid/gbraid/wbraid за 63 дні.
  Google Ads сам забирає файл щодня (Інструменти → Менеджер даних → HTTPS → Конверсії → офлайн). Колонки:
  `gclid, gbraid, wbraid, conversion_time (ISO з часовим поясом), conversion_value, currency_code, order_id, conversion_name`.
  Той самий клік повторно не рахується. Старий шаблон «Завантаження → Розклади» — `?format=legacy`.
  Той самий файл також за адресою `/conversions/quick-order-purchases.csv` (її використовує підключення в Менеджері даних).
- **Звірка з Meta:** `GET /conversions/meta-purchases.csv` (той самий логін і пароль; `?from=YYYY-MM-DD` — з дати) —
  усі покупки, передані в Meta: швидкі замовлення й Instagram Direct, з номером замовлення, ID у KeyCRM, `event_id`,
  часом події за Києвом, сумою, `content_ids`, товаром і станом відправки. Без телефонів та імен.

Форма тепер зберігає значення gclid/gbraid/wbraid і fbclid (60 днів), а при відправці додає cookie `_fbc`, `_fbp`,
`_ga`, `_ga_<потік>` і user-agent (gbraid/wbraid поки лише зберігаються, у файл Google Ads не потрапляють).
Збої каналу повторюються з паузою до 1 години, доки покупка не застаріє для каналу; на 5-й невдалій спробі
в групу приходить одне попередження. Канали не блокують один одного.

Без `CONVERSIONS_FROM` зараховуються лише замовлення, створені після першого ввімкнення, щоб старі оплачені
замовлення не пішли в рекламу як нові покупки. Замовлення, якого ще немає в KeyCRM, не зараховується, доки
статус не можна перевірити. У тестовому режимі файл для Google Ads порожній.
Лічильники видно в `GET /status` (`purchases`). Змінні — у `.env.example`, розділ «Покупка для реклами».
Перший запуск: `CONVERSIONS_ENABLED=1` + `CONVERSIONS_DRY_RUN=1` + `META_TEST_EVENT_CODE`, перевірити лог і
«Тестові події» в Meta, потім прибрати тестові змінні.
Покупки, що пішли в Meta з тестовим кодом, у рекламі не рахуються. Щоб переслати їх як справжні, задайте
`CONVERSIONS_RESEND_META_BEFORE=<ISO-дата>` (без `META_TEST_EVENT_CODE`): сервер один раз поставить у чергу всі
відправлені покупки, зараховані до цієї дати, з тими самими `event_id` (Meta прибере дублі). Результат — у
`/status` (`conversions.meta_resend`); після цього змінну можна прибрати.

**Instagram Direct та інші джерела KeyCRM** (`CONVERSIONS_CRM_SOURCE_IDS`, напр. `198`): раз на 15 хв сервер
переглядає замовлення цих джерел у KeyCRM і так само зараховує оплачені з ТТН (без групи «Скасовано» і без тегу
`CAPI`, яким позначала відправлені стара інтеграція). Вони йдуть лише в Meta (`action_source: system_generated`,
`event_id = keycrm-<id>`, хеші телефону, імені й міста, сума з KeyCRM у гривнях): для GA4 і Google Ads у таких
замовлень немає ні сесії, ні кліку.

**Ручні швидкі замовлення** (`CONVERSIONS_CRM_MANUAL_QUICK`, за замовчуванням увімкнено): менеджери інколи заводять
замовлення в джерело швидких замовлень (`KEYCRM_SOURCE_ID`) вручну - без номера `quick-…`, часто замість видаленого
замовлення бота. Бот таких замовлень не знає, тому їх зараховує той самий 15-хвилинний перегляд KeyCRM, що й Direct.
Замовлення бота (номер `quick-…` або id, збережений у базі бота) тут пропускаються - їх рахує основний цикл.

## Резервні копії бази

Раз на добу (після 04:00 за Києвом) сервер робить знімок бази в `/data/backups/quick-order-РРРР-ММ-ДД.db` (зберігає останні 7).
Якщо задано `BACKUP_CHAT_ID`, стиснутий файл (`.db.gz`) надсилається ще й у цей приватний чат Telegram,
щоб копія пережила втрату диска. Чат має бути **приватним**: у базі телефони й імена клієнтів.
Відновлення: розпакувати `.gz`, покласти файл як `/data/quick-order.db` (сервер зупинити), запустити.

## Нагадування про термін зберігання посилки

Кожні 30 хв сервер питає Нову пошту (`getStatusDocuments`, до 100 ТТН за запит) про створені накладні.
Коли посилка у відділенні чи поштоматі (код 7/8) і до початку платного зберігання (`DatePayedKeeping`) лишилась доба або менше,
менеджер отримує одне повідомлення у відповідь на замовлення: «Напишіть клієнту». Кінцеві статуси
(отримано, відмова, повернення, видалено) більше не опитуються. Якщо Нова пошта не віддає `DatePayedKeeping`, нагадування не надсилається.

## Розумний підбір розміру, «розмір як минулого разу», найближчі відділення, A/B-тести форми

- **Підбір розміру за історією** (`GET /proxy/size`). Коли клієнт вводить зріст і вагу, сервер шукає в замовленнях цього ж магазину схожих покупців
  (допуск ±4…10 см і кг), які купили (оплата чи ТТН) і не повернули посилку (коди Нової пошти 102/103/105/106 і статуси «спам», «скасовано» не рахуються).
  Рекомендація з'являється, коли набралось не менше `SIZE_ADVISOR_MIN` (5) схожих покупців і один розмір має частку ≥ 40%. Назовні йдуть лише розмір, відсоток і кількість.
  Інакше працює звичайна таблиця розмірів із налаштувань блоку.
- **«Ваш розмір, як минулого разу»** (`POST /proxy/lastsize`). За номером телефону форма пропонує розмір останньої купленої й не поверненої речі
  (окремо футболки й худі). Віддається лише розмір; не більше 10 запитів за 10 хв з однієї адреси; клієнт сам натискає «Обрати».
  На телефоні номер вводять на другому кроці, тому пропозиція одразу видна тим, чий номер збережений у браузері.
- **Найближчі відділення і поштомати.** Кнопка «📍 Найближчі до мене» під полем відділення просить дозвіл на геолокацію й сортує точки обраного міста
  за відстанню (координати йдуть лише для сортування й ніде не зберігаються).
- **A/B-тест форми** (`GET /proxy/ab`). Кожен відвідувач (випадковий ідентифікатор у браузері, без персональних даних) постійно бачить один варіант.
  Зараз тестується текст кнопки: «Замовити» проти «Підтвердити замовлення» (`server/experiments.js`, там же можна додати тест).
  Коли на кожен варіант набралось `AB_MIN_VIEWS` (300) показів, разом не менше `AB_MIN_CONVERSIONS` (20) замовлень і різниця значуща (p < 0,05),
  переможець автоматично стає єдиним варіантом, а менеджерам приходить повідомлення. Якщо за `AB_MAX_VIEWS` (3000) показів на варіант різниці немає,
  лишається поточний. Поточні цифри: `GET /status` → `experiments`. Вимкнути: `AB_ENABLED=false`.

Для клієнтської частини (кнопки, підбір, геолокація, A/B) треба оновити розширення Shopify (`app deploy`); серверна частина оновлюється на Render сама.
